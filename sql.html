01. Введение в SQL

История, стандарты, категории команд, зачем нужен SQL сегодня.

📖 Что такое SQL

SQL (Structured Query Language) — декларативный язык для управления реляционными базами данных. Создан в IBM в 1970-х на основе реляционной модели Эдгара Кодда. Стандартизирован ANSI в 1986 и ISO в 1987.

В отличие от императивных языков (Python, Java), где вы указываете как делать, в SQL вы описываете какой результат хотите получить. СУБД сама решает, как его вычислить.

Реляционная модель: данные организованы в таблицы (отношения) со строками (кортежами) и столбцами (атрибутами). Связи между таблицами задаются через ключи.

📅 История SQL

1970 Эдгар Кодд публикует реляционную модель данных
1974 IBM создаёт SEQUEL (позже SQL) для System R
1979 Oracle V2 — первая коммерческая реляционная СУБД
1986 SQL стандартизирован ANSI
1992 SQL-92 — самый важный стандарт до сих пор
1999 SQL:1999 — оконные функции, CTE, регулярные выражения
2003 SQL:2003 — XML, оконные функции расширены
2016 SQL:2016 — JSON, row pattern matching
2023 SQL:2023 — property graph queries, JSON enhancements

💡 Интересные факты

  • SQL читается почти как английский: SELECT name FROM users WHERE age > 18.
  • Вопреки мифу, SQL не регистрозависим для ключевых слов: SELECT, select и Select эквивалентны.

  • Несмотря на NoSQL-бум, SQL остаётся №1 языком для структурированных данных и аналитики.

Обратите внимание: в SELECT перечисляются столбцы, в FROM — таблица, в WHERE — фильтр по строкам. Порядок ключевых слов важно соблюдать.

🧠 Углублённый разбор: Модель мышления SQL

SQL описывает множество строк, удовлетворяющих условиям, а не последовательность действий над каждой строкой. Поэтому полезно сначала определить требуемый результат, затем источник, фильтры, группировку и порядок выдачи. Реляционная таблица не обязана иметь физический порядок строк.

Реляционная модель опирается на отношения и логические ограничения. Первичный ключ идентифицирует строку, внешний ключ выражает связь, а ограничения помогают базе отклонять некорректные состояния независимо от приложения.

02. Установка и СУБД

PostgreSQL, MySQL, SQLite: что выбрать для обучения и продакшена.

📖 Какие бывают СУБД

Реляционные: PostgreSQL, MySQL/MariaDB, SQLite, Oracle, Microsoft SQL Server. Не совсем реляционные: CockroachDB, YugabyteDB (distributed SQL). NoSQL: MongoDB, Cassandra, Redis (не SQL, но стоит знать).

03. SELECT: базовый запрос

SELECT, алиасы (AS), DISTINCT, вычисляемые столбцы.

📖 Анатомия SELECT

SELECT — основная команда чтения. Минимальный запрос: SELECT * FROM table_name;.

Порядок обработки в SQL-движке (важно для понимания логики):

FROM → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

Столбцы можно переименовывать через AS alias: SELECT name AS full_name. Псевдоним не обязательно, но полезно для вычисляемых столбцов.

DISTINCT убирает дубликаты строк в результате. * — все столбцы (не рекомендуется в продакшене — лишние данные).

🧭 Практический кейс: Выборка с осмысленными алиасами

Явные алиасы делают результат читаемым в отчётах и API.

SELECT first_name || ' ' || last_name AS full_name, salary * 12 AS annual_salary FROM employees;

Оператор || — конкатенация строк в PostgreSQL/Oracle. В MySQL используется CONCAT().

🧠 Углублённый разбор: Проектирование читаемой выборки

Выбирайте только необходимые поля и давайте вычисляемым значениям понятные псевдонимы. Это снижает объём передаваемых данных и делает контракт результата стабильнее для отчётов, экспорта и API. DISTINCT следует применять осознанно: он может скрывать проблему дубликатов в исходных данных.

Если в SELECT есть арифметика или объединение строк, явно учитывайте NULL и правила конкретной СУБД. Выражение с NULL часто возвращает NULL, поэтому для вывода запасного значения используют COALESCE.

SELECT name, salary * 12 AS annual_salary FROM employees;

AND/OR/NOT, IN, BETWEEN, LIKE, IS NULL, сравнения.

📖 Основы WHERE

WHERE фильтрует строки до их попадания в результат. Условие — любое логическое выражение. Работает по трёхзначной логике SQL: TRUE, FALSE, NULL.

Операторы сравнения: =, <> или !=, <, >, <=, >=.

Логические: AND, OR, NOT. Приоритет: NOT → AND → OR. Для явности используйте скобки.

Специальные: IN (список), BETWEEN (диапазон, включительно), LIKE (шаблон), IS NULL / IS NOT NULL, EXISTS (подзапрос).

NULL — это не значение, а «неизвестность». Поэтому column = NULL всегда даёт UNKNOWN (не TRUE). Правильно: IS NULL.

05. ORDER BY и LIMIT

Сортировка, ASC/DESC, NULLS FIRST/LAST, пагинация.

📖 Теория

ORDER BY сортирует результат. ASC — по возрастанию (по умолчанию), DESC — по убыванию. Можно сортировать по нескольким столбцам: ORDER BY dept ASC, salary DESC.

LIMIT n — вернуть только первые n строк. OFFSET m — пропустить первые m. Вместе — классическая пагинация: LIMIT 10 OFFSET 20 (третья страница по 10).

Стандарт SQL: OFFSET m ROWS FETCH NEXT n ROWS ONLY. Но LIMIT/OFFSET короче и поддерживается в PostgreSQL, MySQL, SQLite.

NULL в сортировке: в PostgreSQL по умолчанию NULL считается больше любого значения (в ASC — в конце). Управляется: NULLS FIRST / NULLS LAST.

🎮 Интерактив: визуализатор сортировки

06. Агрегатные функции

COUNT, SUM, AVG, MIN, MAX, COUNT(*), COUNT(DISTINCT), NULL.

📖 Теория

Агрегатные функции сворачивают набор строк в одно значение. Основные: COUNT, SUM, AVG, MIN, MAX.

COUNT(*) считает все строки, COUNT(column) — только не-NULL значения. COUNT(DISTINCT column) — уникальные не-NULL.

NULL в агрегатах: SUM/AVG/COUNT игнорируют NULL. Если нужна замена — используйте COALESCE(column, 0).

07. GROUP BY и HAVING

Группировка, агрегаты по группам, HAVING vs WHERE, ROLLUP.

📖 Теория

GROUP BY объединяет строки с одинаковыми значениями в группы. К каждой группе применяются агрегаты: COUNT, SUM, AVG, MIN, MAX.

Правило: все столбцы в SELECT должны быть либо в GROUP BY, либо внутри агрегатной функции.

HAVING фильтрует уже сгруппированный результат. WHERE фильтрует строки ДО группировки.

FROM → WHERE → GROUP BY → HAVING → SELECT

ROLLUP / CUBE — расширения для итогов: GROUP BY ROLLUP(dept) добавляет строку с общим итогом по всем отделам.

🎮 Интерактив: группировка

📐 Примеры

-- Средняя зарплата по отделам SELECT dept, AVG(salary) AS avg_salary FROM employees GROUP BY dept; -- Несколько агрегатов SELECT dept, COUNT(*) AS total, AVG(salary) AS avg_salary, MAX(salary) AS max_salary FROM employees GROUP BY dept; -- HAVING: только отделы с 3+ сотрудниками SELECT dept, COUNT(*) AS cnt FROM employees GROUP BY dept HAVING COUNT(*) >= 3; -- WHERE + GROUP BY + HAVING SELECT dept, AVG(salary) AS avg_salary FROM employees WHERE hire_date >= '2020-01-01' GROUP BY dept HAVING AVG(salary) > 80000;

08. JOIN: соединения

INNER, LEFT, RIGHT, FULL, CROSS, SELF, USING, ON.

📖 Теория

JOIN объединяет строки двух (или более) таблиц по условию. Основные виды:

  • INNER JOIN — только совпадающие строки
  • LEFT JOIN — все строки левой + совпадающие правой (NULL, если нет)
  • RIGHT JOIN — все строки правой + совпадающие левой
  • FULL JOIN — все строки из обеих таблиц
  • CROSS JOIN — декартово произведение (без условия)
  • SELF JOIN — соединение таблицы с самой собой

ON — условие соединения. USING (column) — краткая форма, если имя столбца одинаковое.

📐 Примеры

09. Подзапросы

IN, EXISTS, скалярные, коррелированные, ANY/ALL.

📖 Теория

Подзапрос — SELECT внутри другого запроса. Может возвращать:

  • Скаляр (одно значение) — используется как значение
  • Столбец — с операторами IN, ANY, ALL
  • Таблицу — в FROM (derived table)

Коррелированный подзапрос — ссылается на столбцы внешнего запроса. Выполняется для каждой строки. Может быть медленным, но иногда незаменим.

EXISTS — проверяет наличие хотя бы одной строки. Часто быстрее IN с подзапросом на больших данных.

🎮 Интерактив: подзапрос

10. CTE и WITH

Общие табличные выражения, рекурсивные CTE, читаемость.

📖 Теория

CTE (Common Table Expression) — именованный подзапрос, объявленный в WITH перед основным запросом. Улучшает читаемость и позволяет ссылаться на результат несколько раз.

Рекурсивный CTE — WITH RECURSIVE: CTE ссылается на самого себя. Классические применения: иерархии, деревья, графы, генерация последовательностей.

CTE не материализуется по умолчанию (в PostgreSQL с версии 12 — inline-оптимизация). Материализацию можно принудить: AS MATERIALIZED.

🎮 Интерактив: CTE-визуализатор

11. Оконные функции

OVER, PARTITION BY, ROW_NUMBER, RANK, LAG/LEAD, SUM OVER.

📖 Теория

Оконные функции вычисляют значение по «окну» строк, не сворачивая результат в одну строку (в отличие от агрегатов с GROUP BY).

Синтаксис: func() OVER (PARTITION BY ... ORDER BY ... ROWS BETWEEN ...).

Ранжирующие: ROW_NUMBER (уникальный), RANK (с пропусками), DENSE_RANK (без пропусков), NTILE (разбиение на N групп).

Смещённые: LAG (предыдущая), LEAD (следующая), FIRST_VALUE, LAST_VALUE.

Агрегатные оконные: SUM, AVG, COUNT с OVER — например, накопительный итог.

🎮 Интерактив: оконные функции

SELECT name, salary, ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn FROM employees;

📐 Примеры

-- Нумерация внутри отдела SELECT name, dept, salary, ROW_NUMBER() OVER ( PARTITION BY dept ORDER BY salary DESC ) AS rn FROM employees; -- Топ-1 по зарплате в каждом отделе WITH ranked AS ( SELECT *, ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn FROM employees ) SELECT * FROM ranked WHERE rn = 1; -- Накопительный итог SELECT id, amount, SUM(amount) OVER (ORDER BY id) AS running_total FROM orders; -- LAG: разница с предыдущим заказом SELECT id, amount, amount - LAG(amount) OVER (ORDER BY id) AS diff FROM orders;

  • FOREIGN KEY — ссылка на PK другой таблицы. Обеспечивает ссылочную целостность.
  • UNIQUE — уникальность значения (или комбинации столбцов).
  • CHECK — логическое условие, которое должно быть TRUE.
  • NOT NULL — запрет NULL.
  • DEFAULT — значение по умолчанию.

16. Индексы

B-tree, hash, составные, частичные, covering, EXPLAIN.

📖 Теория

Индекс — структура данных для ускорения поиска. Как алфавитный указатель в книге. Основной тип в PostgreSQL/MySQL — B-tree.

  • B-tree — диапазонные запросы, =, <, >, BETWEEN, ORDER BY
  • Hash — только равенство (=). Компактнее, но не поддерживает диапазоны
  • GIN / GiST — полнотекстовый поиск, JSONB, массивы
  • BRIN — очень большие таблицы с корреляцией (например, время)

Составной индекс (col1, col2) работает для запросов по col1 или (col1, col2), но не по col2 отдельно (правило левого префикса).

Covering index содержит все столбцы запроса — БД может отдать результат без обращения к таблице (Index Only Scan).

Частичный индекс — WHERE внутри индекса, например только активные записи.

🎮 Интерактив: влияние индекса

Строк в таблице: 1 000 000
Без индекса (Seq Scan): ~50 000 μs
С индексом (Index Scan): ~5 μs
Ускорение: 10 000×

📐 Примеры

-- Обычный индекс CREATE INDEX idx_users_email ON users (email); -- Уникальный CREATE UNIQUE INDEX uq_users_email ON users (email); -- Составной CREATE INDEX idx_orders_user_date ON orders (user_id, created_at DESC); -- Частичный CREATE INDEX idx_active_users ON users (email) WHERE deleted_at IS NULL; -- Covering index (PostgreSQL) CREATE INDEX idx_orders_covering ON orders (user_id) INCLUDE (amount, created_at); -- Hash-индекс CREATE INDEX idx_hash_email ON users USING HASH (email); -- GIN для JSONB CREATE INDEX idx_data_gin ON events USING GIN (data); -- Удалить DROP INDEX idx_users_email;

⚠️ Когда индекс НЕ помогает

  • Много NULL в столбце — индекс их не хранит (в B-tree)
  • Функция над столбцом: WHERE LOWER(email) = 'a@b' не использует индекс по email — нужен функциональный индекс
  • Низкая селективность (boolean, страна с 2 значениями) — Seq Scan быстрее
  • Маленькие таблицы — планировщик выберет Seq Scan
  • Неявное приведение типов: WHERE id = '42' — иногда ломает индекс

17. Транзакции и ACID

BEGIN, COMMIT, ROLLBACK, SAVEPOINT, ACID-свойства.

📖 Теория

Транзакция — набор операций, выполняемых как единое целое: либо все, либо ничего.

ACID:

  • Atomicity (атомарность) — всё или ничего
  • Consistency (согласованность) — данные соответствуют ограничениям
  • Isolation (изоляция) — параллельные транзакции не видят незакоммиченных изменений друг друга
  • Durability (надёжность) — после COMMIT данные сохранены даже при сбое

SAVEPOINT — промежуточная точка, к которой можно откатиться без отмены всей транзакции.

19. Нормализация

1НФ, 2НФ, 3НФ, BCNF, денормализация.

📖 Теория

Нормализация — процесс устранения избыточности и аномалий в схеме БД.

  • 1НФ — атомарные значения (нет массивов/списков в столбце)
  • 2НФ — 1НФ + каждый неключевой столбец зависит от всего первичного ключа
  • 3НФ — 2НФ + нет транзитивных зависимостей (A → B → C)
  • BCNF — строже 3НФ: каждый детерминант — потенциальный ключ
  • 4НФ, 5НФ — про многозначные зависимости и соединения

На практике 3НФ достаточно для 95% случаев. Дальше — сознательная денормализация.

20. OLAP, OLTP, денормализация

Хранилища данных, звёздная схема, Data Warehouse.

Data Warehouse — отдельное хранилище для аналитики, куда регулярно переливаются данные из OLTP (ETL/ELT).

Звёздная схема (star schema): центральная fact table + dimension tables вокруг. Снежинка (snowflake) — нормализованные измерения.

23. Триггеры

📖 Теория

Триггер — код, автоматически выполняемый при INSERT/UPDATE/DELETE. Привязывается к таблице и событию.

28. Партиционирование и шардирование

Секционирование таблиц, диапазоны, hash, шардирование.

📖 Теория

Партиционирование — разделение большой таблицы на физические части (партиции) с единым логическим интерфейсом. Ускоряет запросы, упрощает purge старых данных, распределяет нагрузку.

Виды: RANGE (по диапазону — обычно даты), LIST (по значению — страна, регион), HASH (по хешу ключа).

Шардирование — распределение данных по разным серверам (горизонтальное масштабирование). В отличие от партиций — на разных машинах.

🎮 Интерактив: визуализатор партиций

📐 Примеры

-- RANGE по дате CREATE TABLE orders ( id BIGSERIAL, created_at DATE NOT NULL, amount NUMERIC ) PARTITION BY RANGE (created_at); CREATE TABLE orders_2023 PARTITION OF orders FOR VALUES FROM ('2023-01-01') TO ('2024-01-01'); CREATE TABLE orders_2024 PARTITION OF orders FOR VALUES FROM ('2024-01-01') TO ('2025-01-01'); -- LIST по стране CREATE TABLE users ( id BIGINT, country TEXT NOT NULL ) PARTITION BY LIST (country); CREATE TABLE users_ru PARTITION OF users FOR VALUES IN ('RU'); CREATE TABLE users_us PARTITION OF users FOR VALUES IN ('US'); -- HASH по id CREATE TABLE events ( id BIGINT, data JSONB ) PARTITION BY HASH (id); CREATE TABLE events_p0 PARTITION OF events FOR VALUES WITH (MODULUS 4, REMAINDER 0); -- и p1, p2, p3 -- Удаление старой партиции — мгновенно DROP TABLE orders_2022;
